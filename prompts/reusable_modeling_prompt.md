# 发送给 Codex 的 mathmodeling skills 分问执行 Prompt

## 使用方法

在一个新的数学建模项目中，把下面整个代码块作为首条任务要求发送给 Codex，并同时提供题目与附件。它的作用是改变 mathmodeling skills 的执行顺序和材料输出方式：先为所有小问建立模型，再按小问或强关联问题组逐个完成，且持续记录建模/选模全过程。

```text
请使用当前环境中已安装的 mathmodeling skills 完成本数学建模项目。如果这些 skills 不可用或无法读取，请先明确说明，不要假装已经调用。

本项目采用以下强制工作流。它是对 mathmodeling skills 的编排要求，不替代各 skill 的证据、安全、人工决策和验收规则。

【核心目标】
1. 初始阶段先为全部小问建立可审阅的初步模型，而不是只处理第一问，也不是只做题目目录。每问至少要有：目标与输出、数据来源、决策变量、参数、目标函数、核心约束、与其他小问的依赖、主候选方法、可用 baseline、主要风险和待人工判断项。
2. 初始建模完成后，不要一次性生成或运行全部小问的代码。按依赖顺序逐问闭环：详细调整当前问建模 → 当前问方法确认 → 当前问代码与审查 → 当前问实验 → 当前问稳健性检验 → 当前问结果判断；完成后才进入下一问。
3. 若几个小问存在强耦合，可把它们组成一个问题组，共同建立共享变量、约束、情景或递推关系；但仍需说明为什么必须分组，并分别保存各小问的模型边界、代码入口、结果、稳健性证据和结论。不得借“有关联”为由一次运行所有问题。
4. 在问题解析、模型建立和模型选择的每一个实质步骤，持续生成一份可写进论文、方便人查看、也可直接交给其他 AI 接续的“解题过程/思路”材料。不能只留下最终模型卡、JSON 状态或聊天摘要。

【第一阶段：全题建模，不生成全题代码】
依次调用或遵循以下 mathmodeling skills：
- workflow-orchestrator：建立每问 manifest、依赖顺序和当前唯一行动；
- problem-parser：解析全部小问的目标、对象、数据、约束和输出；
- problem-classifier：识别每问的任务类型，不在此步直接定算法；
- data-auditor-cleaner：统一完成附件映射、数据质量和每问数据就绪度；
- symbol-table-builder：建立跨小问一致的符号和单位；
- model-assumptions-builder：区分题面条件、数据事实、人工假设和模拟设定；
- method-selector：为每问建立主候选、可用 baseline 和至多一个有明确触发条件的备用方法，并完成必要风险探针；
- decision-prompt-builder：只在真正需要人工取舍时展示选择卡。

第一阶段必须产出“所有小问的初步模型包”，足以让人检查每问的变量、目标、约束、方法链和依赖关系。此时不得批量生成所有小问代码，也不得把 AI 推荐当成人工决定。

【第二阶段：确定执行单元与顺序】
根据依赖关系，把任务划分为 Q1、Q2、Q3……或少数强关联问题组。输出：
- 执行顺序；
- 每个问题组的分组理由；
- 哪些部分共享、哪些必须独立；
- 当前只激活哪一问/哪一组；
- 为什么其他问题此时不能进入代码阶段。

默认一次只激活一个执行单元。未激活问题允许维护模型草案和依赖说明，但不得生成正式代码、运行实验或提前写最终结论。

【第三阶段：按问/问题组逐个闭环】
对当前执行单元按以下顺序工作：
1. 详细调整本问模型：核对数据口径、变量、目标函数、约束、边界、求解规模和与前问的接口。
2. 更新本问的方法筛选证据和风险探针；比较主候选与真正能完成同一任务的 baseline。
3. 使用 decision-prompt-builder 展示互斥选项，等待用户最终确认。用户说“倾向”“暂定”“以后补充”时，只在建模过程文档和 manifest 中忠实标记为 PROVISIONAL，不得让 modeler-decision-logger 把它写成 `DECIDED`，也不得视为 G2.5 已通过。只有用户明确作出最终选择后，才由 modeler-decision-logger 追加正式决策。
4. 仅在本问方法被人工明确确认后，调用 model-code-analyzer 形成实现契约，再调用对应的 Python/MATLAB code generator 生成并运行当前问的主方法与 baseline。
5. 调用对应 code reviewer 检查语法、输入契约、模型一致性、可复现性和输出契约。
6. 调用 result-report-generator 比较主方法与 baseline；调用 robustness-checker 做针对模型风险的敏感性、误差、压力和失效条件检查。
7. 把正式证据交给用户选择继续、调整或启用备用方法。结果未确认时不冻结、不进入下一问最终实现。
8. 当前问完成后，更新其 manifest 和交接材料，再激活下一问。不得把后续问夹带进当前问的一次求解。

【解题过程/思路文档：必须持续生成】
为全题维护一份人读总览，例如：
- planning/solution_process/global_modeling_map.md

为每一问维护一份持续更新、而不是每步新建碎片文件的主文档，例如：
- methods/Q1/q1_modeling_process.md
- methods/Q2/q2_modeling_process.md

每完成一个建模或模型选择的实质步骤，立即更新对应文档。每份文档至少包含：
1. 本问要解决什么，以及它与其他小问的关系；
2. 题面事实、数据观察、人工补充、建模假设、模拟设定的明确区分；
3. 从文字条件到变量、参数、目标函数和约束的推导过程；
4. 候选方法为何适用、为何可能失败、风险探针发现了什么；
5. baseline 为什么是可比的完整方法，而不是装饰性参照；
6. 人工选择原话、选择状态和证据路径；
7. 当前模型相对上一版改了什么、为什么改、影响哪些下游环节；
8. 可直接改写进论文的段落、公式与算法流程，但必须标注 DRAFT/VERIFIED，未验证内容不得写成结论；
9. 方便另一 AI 接续的当前状态、必读文件、已完成事项、未决问题和唯一下一步。

这份人读文档与 manifest、JSONL 决策账本、risk_probe_summary、run_summary 等机器证据同时存在：人读文档负责解释“为什么和怎么做”，机器文件负责精确状态与可追溯证据。不要用机器 JSON 代替解题思路，也不要让人读文档脱离证据路径自行编造数字。

【论文材料要求】
- 建模阶段可以逐步形成论文可用的“问题分析、模型假设、符号说明、模型建立、方法选择理由和算法流程”草稿。
- 草稿中的数值、结果和结论必须标记证据状态；正式论文只能使用经过代码审查、稳健性检验和冻结的结果。
- 每问闭环后，使用 final-method-explainer 和 solution-package-builder 整理可交给 paper-section-writer 的权威材料；paper-section-writer 不得从零散实验目录猜测结论。
- 最终统一检查跨小问符号、单位、共享参数、数字和主张的一致性。

【交互与停止规则】
- AI 负责机械检查，人负责方法取舍、假设必要性、结果接受和论文主张。
- 每次只提出当前阶段真正阻塞的选择，最多三个问题；不要把可由数据或计算确定的事项推给用户。
- 到达人工决策点时停止跨门推进，但先完成所有安全、只读或机械性检查。
- 不因当前问完成部分工作就跳到后续问；也不因后续问已有草模就提前生成其代码。
- 每次回复必须说明：当前执行单元、当前 gate、这次更新了哪些人读/机器材料、证据状态、阻塞项和唯一下一步。

【文件与版本控制】
- 所有成果只写入当前项目指定目录，原始数据保持只读。
- 若项目要求 Git 同步，则每次文件修改后必须在同一阶段完成验证、提交和推送，并核对本地 HEAD、远端分支及交付文件树一致；不一致时不得声称完成。

现在先检查项目中的题目、附件、现有 mathmodeling artifacts 和项目级 AGENTS.md。然后执行第一阶段，为所有小问建立初步模型和人读解题过程总览。完成全题初步建模后，向我展示问题依赖、建议执行顺序和第一个真正需要人工决定的选择；在我回答前不要批量生成代码。
```
